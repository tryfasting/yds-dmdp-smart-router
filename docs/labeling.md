# Labeling — 학습 데이터를 어떻게 만들었나

라우팅 모델의 학습 데이터 7,701건이 어디서 왔고, 어떤 프롬프트로 라벨을 붙였고, 그 설계가 왜 모델의 태그 의존으로 이어졌는지 기록합니다. 당시 코드는 [research/labeling/](../research/labeling/)에 있습니다(본인 작성 원본). 아래 분포 수치는 `smartrouter audit-labels`로 재현합니다.

## 1. 가설과 입력 형식

서비스 로그를 보면, 요청 난이도나 사용자 의도와 무관하게 대부분의 트래픽이 경량 모델로 가고 있었습니다. 새로 쓰기 수준의 Strong 요청이나 분야별 교정 요청도 마찬가지였습니다.

가설은 사용자가 고른 강도·분야를 의도 z로 보고, 교정 전 문장 x와 함께 넣어 모델을 배정하는 것입니다(y = f(x, z)). 입력 형식은 `[강도] [분야] 문장`입니다.

## 2. 데이터가 두 갈래인 이유

| 구분 | 출처 | 행 | 강도·분야 | 라벨 프롬프트 |
|---|---|---:|---|---|
| v1 `source_v1_legacy` | 서비스 로그 `문장교정기록.json` | 1,053 | 사용자가 실제로 고른 값 | V4: 강도·분야·원문·교정문 |
| v2 `source_v2_augmented` | 스타트업이 자사 서비스로 유튜브 등 자체 콘텐츠를 교정한 문장 쌍 `munch_data/*.csv` | 6,648 | 없음 → 강도 역산, 분야 NONE | V3: 원문·교정문만 |

**서비스 로그만으로는 1,000건 남짓이라 학습 데이터가 절대적으로 부족했습니다.** 스타트업이 함께 준 교정 문장 쌍은 양이 충분했습니다. 하지만 DB를 거치지 않은 기록이라 강도·분야가 없었고, 입력 형식 `[강도] [분야] 문장`을 채울 수 없었습니다. 그래서 강도를 역산해 붙여 데이터를 되살렸습니다(메타데이터 역공학).

## 3. 라벨링 (Gemini, LLM-as-a-Judge)

- 공통 설정은 다음과 같습니다.
  - temperature 0, 5건 묶음, JSON 스키마(`reasoning`, `score`, `difficulty_label`)
  - 무료 한도를 넘으면 다음 모델로 넘기는 릴레이(flash-lite → flash …)
  - score ≥ 4를 Hard(1)로 정했습니다.
- **V3 (v2용) 루브릭**
  - 1: 기계적 수정(오타·구두점)
  - 2: 조사·단어 교체
  - 3: 기본적인 어순 재배열·작은 구조 변경
  - 4: 어조 변화·큰 구조 변경·격식 조정
  - 5: 전면 재구성·추상적 재작성
- **V4 (v1용)**
  - 교정에 필요한 "지능 수준"을 채점하게 했습니다.
  - "Strong을 요청했는데 결과가 단순하면 낮게, 깊은 추론·어조 전환·창의성이 필요할 때만 높게"라는 규칙을 넣었습니다.
  - 사용자가 고른 강도·분야를 함께 보여 줬습니다.

## 4. 메타데이터 역공학 (v2)

라벨링이 끝난 v2에 `difflib.SequenceMatcher(None, 원문, 교정문).ratio()`로 강도를 붙였습니다.

| 비율 | 강도 |
|---|---|
| > 0.9 | WEAK |
| > 0.6 | MODERATE |
| ≤ 0.6 | STRONG |

분야는 근거가 없어 NONE으로 두었습니다. 이 강도는 사용자의 의도가 아니라 **교정 결과가 얼마나 바뀌었는가**입니다.

## 5. 결과 분포와 태그 의존

`smartrouter audit-labels --csv dataset_master.csv` 결과입니다(`reports/label_distribution.json`).

| 강도 | 행 | Hard 비율 |
|---|---:|---:|
| STRONG | 4,298 | 71.5% |
| MODERATE | 2,520 | 19.0% |
| WEAK | 883 | 1.6% |

- 분야는 7,701행 중 7,456행(96.8%)이 NONE입니다.
- STRONG의 Hard 비율은 실제 선택값인 v1에서 52.2%, 역산값인 v2에서 72.3%입니다.

이 불균형이 태그 의존의 원인입니다.
- 데이터의 86%(v2)에서 강도(변화 비율)와 라벨(V3의 변화 정도 채점)이 **같은 교정 결과**에서 나왔습니다.
- 그래서 학습 데이터 안에서 강도, 변화량, 난이도가 거의 같은 정보가 됐습니다.
- 모델 결정의 99.65%가 "STRONG이면 heavy" 규칙과 같았습니다. 같은 강도 안에서의 판별력은 AUC .618~.667로 약했습니다([decisions.md §4](decisions.md#4-분류기-성능)).

가설과도 어긋납니다.
- 가설은 사용자의 **실제 의도**를 넣는 것이었습니다. 하지만 데이터 대부분에서 강도는 교정 결과로 만든 값이었습니다.
- 실제 서비스에서 강도는 요청 시점에 사용자가 고르는 값이라, 학습 때와 의미가 다릅니다.
- 발표에서는 "변경량이 곧 난이도는 아니다"라며 BLEU를 쓰지 않았습니다. 하지만 강도 태그와 V3 루브릭은 결국 변화 정도를 봤습니다.

## 6. 다시 한다면

- 실제 강도가 남은 서비스 로그를 더 확보하고, 역산 데이터는 `source_origin`으로 구분해 영향을 비교합니다.
- 태그 없이 문장만 넣은 모델, 태그만 쓰는 규칙, 태그와 문장을 함께 넣은 모델을 원문 기준 그룹 분할로 비교합니다.
- 사람이 채점한 소량 샘플로 LLM 라벨과의 일치도를 확인합니다.
- 라벨을 변화량이 아니라 요청 시점 기준(예: 경량 모델 결과가 Judge 기준을 통과하는가)으로 다시 정의합니다.
